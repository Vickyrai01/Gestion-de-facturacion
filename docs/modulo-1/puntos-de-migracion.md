# Puntos de migración para el proyecto paralelo

Inventario conceptual del Módulo 1. Las alternativas son para el futuro sistema .NET 10; ninguna fue implementada en esta rama. La dificultad es una estimación para este ejemplo pequeño: baja supone adaptación local, media exige cambios coordinados y alta afecta el pipeline o varias dependencias.

| Elemento | Situación actual y archivos | Motivo de revisión | Alternativa habitual en .NET 10 | Dificultad estimada |
| --- | --- | --- | --- | --- |
| Plataforma de ejecución | `.csproj` tradicional, `TargetFrameworkVersion=v4.8`; compilación con MSBuild de Visual Studio y CLR de Framework. | Hay que revisar referencias, APIs e imports; cambiar el destino no cambia el framework web. | Proyecto SDK para net10.0 y runtime de .NET moderno. | Media |
| Hosting | IIS Express, configuración web del `.csproj`, `Global.asax` y handler ASP.NET de `Web.config`. | El arranque y la integración HTTP corresponden a ASP.NET clásico. PATCH requiere considerar también el handler del host. | Arranque de ASP.NET Core en `Program.cs`; Kestrel o integración con IIS según despliegue. | Media |
| Routing | `App_Start/RouteConfig.cs`, `RouteCollection`, `{controller}/{action}/{id}` y defaults Home/Index. | Registrar rutas y seleccionar endpoints cambia; hay que conservar URLs y verbos. | Routing de ASP.NET Core y rutas convencionales de controllers, o atributos cuando hagan falta. | Baja |
| Controllers y vistas | `System.Web.Mvc.Controller`, `ActionResult`, `View`, binding, `ModelState`, helpers y motor Razor clásico en `Views/Web.config`. | Se deben adaptar tipos, helpers, generación de enlaces y filtros sin cambiar la intención del CRUD. | Controllers MVC de ASP.NET Core, `IActionResult`, vistas Razor y helpers/Tag Helpers del nuevo framework. | Media |
| Configuración | `Web.config`, transformaciones Debug/Release, binding redirects y proveedor CodeDom. | La configuración de aplicación y el modelo de compilación/ensamblados cambian; IIS puede seguir necesitando su configuración de hosting. | Configuración de Core con appsettings.json, variables de entorno y proveedores; configuración específica de IIS cuando corresponda. | Media |
| Dependencias NuGet | 18 paquetes en `packages.config`; `HintPath` y props hacia la carpeta `packages`; MVC 5, Razor clásico y bundles. | Evaluar paquete por paquete, sus usos y assets; no trasladar todo el inventario automáticamente. | `PackageReference`, framework compartido ASP.NET Core y dependencias que resulten necesarias tras la evaluación. | Media |
| Uso de System.Web | `Global.asax.cs`, controllers, routing, bundles y configuración de vistas usan el stack clásico. | Sus tipos no son las APIs HTTP de Core; la integración no se resuelve con un cambio de namespace aislado. | Pipeline de middleware y `Microsoft.AspNetCore.Http`, MVC Core e inicialización en Program.cs. | Alta |
| Validación y antiforgery | Data Annotations, jQuery unobtrusive, `ValidateAntiForgeryToken`, token y cookie de MVC 5. | Mantener campos requeridos, errores y protección al cambiar filtros/helpers; evaluar soporte del override de verbo. | Data Annotations y antiforgery de Core, con formularios y endpoints definidos explícitamente. | Media |
| Almacenamiento educativo | `Models/ClientesEnMemoria.cs`: colección estática con lock y copias; reinicio por AppDomain. | Aunque no usa System.Web, hay que definir duración, aislamiento y persistencia deseados. | Almacenamiento en memoria equivalente para una primera comparación; persistencia posterior según los módulos. | Baja para conservar la demostración |

El punto de partida y las alternativas MVC se apoyan en la [guía oficial de migración de ASP.NET MVC a Core](https://learn.microsoft.com/en-us/aspnet/core/migration/fx-to-core/examples/overview?view=aspnetcore-10.0). Las diferencias de APIs HTTP están documentadas en [migración de HttpContext](https://learn.microsoft.com/en-us/aspnet/core/migration/fx-to-core/areas/http-context?view=aspnetcore-10.0). Las estimaciones y el inventario de archivos son propios de este repositorio, no garantías de esfuerzo.

## Criterios para comparar ambas aplicaciones

Mantener `/` y `/Clientes`, campos de clientes, estado y operaciones visibles. Probar nuevamente altas y ediciones válidas e inválidas, IDs inexistentes, antiforgery, POST/PATCH, generación de IDs y duración de los datos. Separar incompatibilidad de compilación, incompatibilidad de runtime y diferencia de comportamiento: que un proyecto compile no prueba que preserve su contrato HTTP.

No trasladar automáticamente paquetes de recursos `.es`, CodeDom o herramientas de bundles. Revisar su propósito antes de seleccionar equivalentes; consultar [dependencias.md](dependencias.md). La comparación se hará entre proyectos independientes, conservando el legacy como referencia.
